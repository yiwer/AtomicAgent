# 证据分账

一句「通过」必须说清三件事：哪种证据、在什么条件下取得、还有哪些没验。这个项目把证据拆成九类分别记账，任何一类都不替其他类背书。

## 九类账

| 账 | 怎么算取得 | 不顶替 |
| --- | --- | --- |
| 确定性合约与故障实验 | 替身、受控时钟、并发与故障注入复现状态、重试和保留行为 | 真实引擎与模型 |
| 真实引擎／模型 | 固定 OpenSandbox ＋ Claude SDK／CLI ＋ 获准 profile 实际跑完 | 业务内容正确 |
| 真实网络 | 只读 MCP／来源实际取材，记录获取时间与来源 | 固定快照 |
| 业务内容 | 独立算出文件统计；核对研究结论与本次来源 | 格式校验通过 |
| Docker | 在固定 Linux 节点实测隔离、限额、取消与回收 | gVisor |
| gVisor | 同一工作负载重跑并单独报告 | Docker 的结论 |
| 通知投递 | 受控接收端证明去重、重试与失败回执 | 通道接受，更不等于人已阅读 |
| 浏览器 | Playwright 走通正常、刷新、越权、错误恢复 | 单元测试 |
| 人工验收 | 用户实际体验后给出的明确反馈 | 自动化全绿、工程师目视、goal 自动续接 |

## 结论只有三种

`通过`、`失败`、`未验证`。某一类账没有证据就写 `未验证`，不留空、不顺带写成通过。

同样地，这些都不是结果证据：Agent 自述完成、进程退出 0、日志出现关键字、配置里有那个数字、内部方法被调用过、删除请求已发出。平台的 ValidationReport、权威终态和新鲜完整的资源观测才是。

## 每条结论记什么

输入条件 → 动作 → 外部可观察结果 → 证据出处 → 三种结论之一。外部观察是重点：从对外 API、管理台或真实 provider 资源看得见的事实，不是内部调用轨迹。

## 账放在哪

| 位置 | 内容 |
| --- | --- |
| `.scratch/v0/evidence/ticketNN/` | 原始证据：`verification.md`（验证账本）、`review.md`（双轴审查）、`failure-history.md`（失败与中间实验）、测试输出、截图 |
| `docs/implementation/ticketNN.md` | 该票的实现说明与结论摘要，指向上面的原始证据 |
| `.scratch/v0/issues/NN-*.md` | 验收标准勾选；勾选表示该条已有对应证据 |
| [`.scratch/v0/execution-progress.md`](../../.scratch/v0/execution-progress.md) | 全局索引：每票实现／提交／最终验收状态，以及外部输入缺口 |

推进记录是索引，不是证据本身，也不关闭父规格。

## 现在还缺哪些账

获准模型 profile（endpoint、model、服务端凭据绑定与用途授权）尚未提供，因此「真实引擎／模型」在所有票上都是未验证；gVisor、生产容量和人工验收同样未完成。具体缺口逐项列在推进记录的外部输入账本里。缺账时把确定性路径做完并如实标注，不要用替身结果关闭真实验收。
